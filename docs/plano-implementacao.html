Plano de implementação

O Mapa de Páginas decidiu o quê cada página mostra. Este documento decide como tudo isso vai ser construído: arquitetura, onde os dados moram, como autenticação e escrita funcionam, estrutura de arquivos, convenções de código, sistema de UI e a ordem em que vamos construir. Nada foi codado ainda.

✓Dados que você cadastra (Metas, Transações, Registros de Compra) são escritos de volta na própria planilha, via um endpoint de escrita no Apps Script — a planilha continua sendo a única fonte de verdade.
✓O app fica restrito à sua conta Google — login obrigatório antes de ver qualquer dado.
✓Chart.js (via CDN, versão fixada) desenha todos os gráficos numéricos — linhas, donuts, barras, área. O calendário de proventos não é um gráfico Chart.js, é um componente HTML/CSS feito à mão (corrigido nesta revisão — a versão anterior deste documento misturava os dois).
✓O site também fica instalável (PWA) — ícone na tela inicial, abre em tela cheia, esqueleto em cache pra abrir rápido mesmo com internet ruim. Dado financeiro nunca é cacheado, só a casca do app (decisão desta revisão).
✓Importar o extrato da B3 usa SheetJS (biblioteca gratuita, licença Apache-2.0, via CDN, versão fixada) rodando 100% no navegador — o arquivo .xlsx nunca é enviado a um servidor terceiro, só processado localmente antes de gravar na planilha.
✓Sincronização do histórico de patrimônio tem duas origens pro mesmo processo — gatilho diário automático e botão manual no site — e um registro de status de 3 estados (Sucesso/Atenção/Erro), com nova tentativa que reprocessa só os ativos que falharam.

Camada de dados — Apps Script Web App

Um único projeto Apps Script vinculado à planilha, com duas portas de entrada: leitura (doGet) e escrita (doPost). As duas exigem um token válido antes de fazer qualquer coisa.

Verificação de acesso (todo request, leitura ou escrita)

O front-end manda o token de identidade do Google (que o Google Identity Services devolveu no login) junto de cada chamada. O Apps Script:

  • Confere o token com o próprio Google (endpoint público de verificação), sem precisar de biblioteca extra.
  • Confirma que o e-mail do token é exatamente o seu e-mail (guardado como uma constante no código do script) — qualquer outra conta Google é recusada.
  • Só depois disso executa a ação pedida; caso contrário devolve um erro e o front-end volta pra tela de login.

O Web App é publicado como "Executar como: Eu" e "Quem tem acesso: Qualquer pessoa" — isso soa contraintuitivo, mas é de propósito: deixamos o Google cuidar só do transporte, e a checagem de identidade real é essa verificação de e-mail acima, que funciona de forma confiável com fetch() comum (a alternativa nativa do Apps Script, restringir "quem tem acesso" à sua conta Google, depende de cookies de sessão entre domínios — e isso é bloqueado por navegadores modernos com frequência. Prefiro não depender disso.).

Correção importante desta revisão: o token não pode ir num header Authorization — isso dispara um preflight CORS (requisição OPTIONS) que o Apps Script não responde corretamente, o mesmo problema que já tínhamos identificado antes com POST em application/json. Então o token vai como parâmetro de URL no doGet (?token=...&action=home) e como campo de formulário comum (application/x-www-form-urlencoded, não JSON) no doPost. Isso mantém as chamadas como "simple requests", sem preflight.

Custo dessa abordagem: cada chamada ao Apps Script agora faz 2 idas à rede dentro da mesma execução — uma pra verificar o token com o Google, outra pra ler/escrever a planilha. Isso soma tempo em cima da lentidão que o Apps Script já tem sozinho (ver Riscos técnicos). Vale considerar, mais adiante, cachear a verificação do token por alguns minutos dentro do próprio script (CacheService) pra não reverificar o mesmo token a cada clique.

Um cálculo que precisa de atenção: Patrimônio Longo Prazo × Renda Emergencial

A ação home precisa separar o patrimônio total em 3 números (Total / Longo Prazo / Renda Emergencial). Ações, FIIs e Ações EUA são sempre "Longo Prazo" — mas dentro de Renda Fixa, a divisão é uma marcação manual por posição (coluna B da aba Carteira Renda Fixa, que tem mais de 5 mil linhas). Somar isso lendo linha por linha a cada chamada do home seria lento e ficaria pior ainda somado à verificação de token (ver acima).

Decisão: em vez de somar na hora dentro do Apps Script, criamos duas fórmulas pequenas de SOMASE direto na planilha (uma pra cada marcação), num canto reservado da própria aba ou numa aba auxiliar nova — a planilha já recalcula isso sozinha, de graça, toda vez que muda algo. O handler home só lê essas duas células prontas, em vez de iterar a tabela inteira. Isso é um trabalho de ~5 minutos direto na planilha quando chegarmos na Fase 1, não precisa ser decidido agora — só registrando aqui que não vamos somar isso em JavaScript.

Auxiliar_app — onde os cálculos agregados vivem

Generalizando a decisão acima: sempre que um valor não é "um campo de uma linha" (ticker, preço, etc.) mas sim uma soma, média, ranking ou série ao longo do tempo, ele mora numa aba nova que você criou — Auxiliar_app — calculado com fórmula direto na planilha, nunca em JavaScript dentro do Apps Script. O handler só lê células/intervalos já prontos. Isso vale pro SOMASE de Renda Emergencial × Longo Prazo (acima), pro Patrimônio nas 3 visões, pro histórico de rentabilidade (próxima seção), e pros agregados por classe que hoje vivem em Aux_dash_* — a diferença é só que os Aux_dash_* já existiam antes do app; Auxiliar_app é onde entra tudo que é novo, específico do app.

Histórico de patrimônio — reconstruído via GOOGLEFINANCE + Transações

Decisão desta revisão: em vez de os gráficos de Rentabilidade (Início, Carteiras, Detalhe do Ativo) começarem vazios, reconstruímos o passado. O GOOGLEFINANCE também busca preço histórico por período — =GOOGLEFINANCE(ticker; "close"; data_início; data_fim) devolve uma linha por dia — mas só funciona como fórmula de célula; o Apps Script não chama isso como função direto. Por isso o processo é: escrever a fórmula temporariamente numa célula de rascunho em Auxiliar_app, forçar o recálculo (SpreadsheetApp.flush()), ler o resultado, limpar a célula. É lento (uma leva de leitura/escrita por ticker), então roda como processo em lote, não em tempo real numa chamada de página.

Algoritmo: pra cada ativo, soma as transações de Transações/Transações - USA em ordem cronológica pra saber quantas unidades você tinha em cada data (quantidade acumulada). Cruza isso com o preço histórico do dia (GOOGLEFINANCE) pra chegar em "valor daquele ativo naquele dia". Soma todos os ativos do dia = patrimônio do dia. Isso roda uma vez (o backfill), grava o resultado numa aba Histórico dentro de Auxiliar_app (uma linha por dia, uma coluna por classe + total), e depois um gatilho diário (Time-driven trigger do Apps Script) só adiciona a linha de hoje — não recalcula tudo de novo.

Renda Fixa fica de fora desse método — título público/privado não tem "preço de mercado" via GOOGLEFINANCE do mesmo jeito que ação/FII. Pra manter simples, o valor histórico de Renda Fixa é aproximado por acréscimo composto pelo CDI/Selic desde a data de aplicação (o histórico diário de CDI/Selic já vem da API do Banco Central, testada e funcionando) — não é o valor exato que apareceria no extrato do banco, mas é consistente com o benchmark que já usamos (CDI+Selic) pra essa classe em todo o app, e é razoável pra um gráfico de tendência.

Benchmarks também precisam de histórico: Ibovespa, IFIX e S&P 500 via GOOGLEFINANCE (mesmo mecanismo de escrever/ler célula); CDI e Selic via API do Banco Central, que já suporta consulta por intervalo de datas (/dados?dataInicial=&dataFinal=) — só testamos a variante "últimos N valores" até agora, falta testar essa.

Limitação conhecida, aceita por ora: eventos corporativos (desdobramento, bonificação, grupamento) podem distorcer a quantidade reconstruída se não forem tratados linha a linha — fica registrado como imprecisão possível no histórico mais antigo, não como bloqueio.

Importação do extrato da B3

Substitui a planilha auxiliar que você usava pra ordenar as transações antes de colar em Transações — só para Brasil. Internacional e Renda Fixa continuam lançados manualmente, como já são hoje (decisão sua, mantida).

Biblioteca: SheetJS (pacote xlsx, licença Apache-2.0, gratuita), carregada via <script src="cdnjs..."> com versão fixada (0.18.5) só na página de Transações Brasil — nenhuma outra página paga esse custo de carregamento. Roda inteiramente no navegador; o arquivo nunca sai da sua máquina.

Fluxo, passo a passo:

  • Você anexa o .xlsx baixado direto do extrato de Negociação de ativos da B3 (dropzone ou seleção de arquivo, ver mockup na Direção Visual).
  • SheetJS lê o arquivo e devolve a planilha como matriz de linhas; o script procura, nas primeiras linhas, o cabeçalho pelo texto ("Data do Negócio" + "Código de Negociação") em vez de uma posição fixa — resistente a pequenas mudanças de layout da B3.
  • Filtra Tipo de Movimentação: só Compra/Venda viram linhas "reconhecidas"; qualquer outro tipo (bonificação, desdobramento, direito de subscrição etc.) vira "ignorada" e nunca é processado automaticamente — mesmo com a antiga macro "Classificar os dados" confirmada como um simples ordenar por data, sem lógica nenhuma pra esses casos, então não víamos por que inventar uma agora.
  • Cada ticker reconhecido é conferido contra a Carteira já carregada (Ações/FIIs) no navegador. Se não existir: a linha fica bloqueada com o aviso "essa ação não existe na carteira, inclua antes de importar" — nunca cria o ativo sozinho (decisão registrada no Mapa de Páginas).
  • Você revisa a prévia — Taxa é o único campo editável (o extrato da B3 não traz esse valor) — e confirma.
  • O front-end manda só as linhas reconhecidas e não bloqueadas pro Apps Script, via doPost importarTransacoesB3 — mesmo transporte já usado nas outras escritas (form-urlencoded, token como campo, sem preflight CORS), com a lista de transações serializada num único campo.
  • O Apps Script grava cada uma em Transações (Brasil) achando a primeira linha vazia por varredura da coluna A — nunca getLastRow() (que erraria por causa do buffer de ~10.800 linhas pré-formuladas) — e escrevendo só as colunas A-F; nenhuma fórmula precisa ser copiada, porque já está pré-preenchida em todas as linhas.
  • O Apps Script confere o ticker de novo, como segunda camada (o navegador pode estar com uma cópia da Carteira desatualizada) — se algum ticker do lote não existir, só aquela linha é rejeitada e reportada de volta; o resto do lote segue normalmente.

Nenhum endpoint novo de infraestrutura — é uma ação a mais dentro do doPost que já existe, protegida pela mesma verificação de token.

Sincronização do histórico de patrimônio

Duas origens acionam a mesma função central (ex. atualizarHistorico()): um gatilho automático e um botão manual no site. Nenhuma delas recalcula o histórico inteiro — só estende a partir de onde parou, igual ao backfill original.

  • Gatilho automático: Time-driven trigger do Apps Script, instalado uma única vez em Implantar → Acionadores → Adicionar acionador (baseado em tempo, timer diário, faixa 10h-11h) — configuração feita direto na UI do Apps Script, não precisa de código de instalação. O seletor de acionadores não tem opção nativa "segunda a sábado", então a própria função confere new Date().getDay() e sai sem fazer nada nos domingos.
  • Botão manual: o site chama doPost sincronizarAgora, que roda exatamente a mesma função — só muda o campo origem gravado no registro (Automático/Manual).
  • O que a função faz, por ativo: descobre a última data já salva em aux_historico-patrimonio pra aquele ticker, calcula o intervalo que falta (última salva + 1 até ontem), busca o preço de fechamento via GOOGLEFINANCE só desse intervalo curto (mesmo mecanismo de rascunho + flush() + leitura do backfill) e grava as linhas novas — nunca recalcula um dia já salvo.
  • Câmbio USD/BRL: buscado uma vez por execução (não por ativo) e reaproveitado pelos 8 tickers USA, já que a cotação do dia é a mesma pra todos.
  • Falha isolada: se um ticker específico falhar (ex. GOOGLEFINANCE devolve erro temporário), a função captura o erro daquele ticker e segue pros outros, em vez de abortar o lote inteiro.
  • Registro de Controle: ao final, a função sobrescreve uma única linha nessa aba com timestamp, origem, status calculado (Sucesso = 0 falhas · Atenção = 1 ou mais falhas, mas não todas · Erro = todas falharam ou um erro geral impediu a execução) e o detalhe (lista dos tickers que falharam, só quando existir).
  • Nova tentativa seletiva: o link "tentar novamente" no painel de sincronização chama a mesma ação sincronizarAgora, mas passando só a lista de tickers que falharam — reprocessa apenas esses, não os 30.

Essa é a mesma peça de trabalho citada na Fase 0 (checklist "Fundação") — registrado aqui em detalhe pra não ficar só como menção solta.

Autenticação no front-end

A biblioteca oficial do Google (Google Identity Services, carregada por <script> — sem instalar nada) desenha um botão "Entrar com Google" na tela de bloqueio inicial. Ao logar, ela devolve um token que identifica você.

  • Onde o token fica: em memória (uma variável no auth.js) e espelhado no sessionStorage, pra sobreviver a um F5 sem pedir login de novo — mas some ao fechar a aba, o que é aceitável pra um app de uso pessoal.
  • Expiração: o token dura cerca de 1 hora. Quando o Apps Script recusa por token vencido, o api.js tenta renovar silenciosamente; se não conseguir, mostra de novo a tela de login.
  • Gate de acesso: o shell.js (compartilhado por todas as páginas) esconde o conteúdo da página até confirmar login válido — ninguém vê nem o esqueleto da tela sem estar autenticado.

Pra essa biblioteca funcionar, você precisa de um Client ID OAuth criado no Google Cloud Console — o passo a passo completo está na seção Pré-implementação, mais abaixo.

Convenções de código

HTML — elementos semânticos (<nav>, <main>, <table> de verdade pras tabelas, não divs), um <h1> por página, lang="pt-BR", ids estáveis em todo campo de formulário, e o blocinho fixo de PWA (manifest + ícone + theme-color, ver seção Progressive Web App) em todo <head>.

CSS — tudo derivado dos tokens em tokens.css (nunca uma cor solta direto numa página); mobile-first; classes reutilizáveis em components.css em vez de repetir estilo em cada arquivo .html.

JavaScript — sem bundler: usamos <script type="module"> nativo do navegador, então cada página importa só o que precisa de api.js/charts.js/etc. com import/export de verdade, sem depender de ordem de <script> nem variáveis globais soltas. Isso exige rodar por um servidor local simples durante o desenvolvimento (npx serve ou python -m http.server) — abrir o arquivo direto (file://) não funciona com módulos ES nem com fetch().

Erros — todo fetch tem tratamento de erro visível (nunca falha em silêncio): um estado de "não consegui carregar, tentar de novo" consistente, definido uma vez em components.css/api.js e reaproveitado em toda página.

Nomenclatura — arquivos e classes CSS em kebab-case, funções e variáveis JS em camelCase.

Git — um commit por página/funcionalidade concluída, nada de segredo versionado (o token de login nunca é seu, é do Google, e o e-mail autorizado fica só no código do Apps Script, que vive fora do repositório do front-end).

Sistema de UI

Identidade visual — seguimos o mesmo sistema de tokens e tipografia já validado nos mockups e nos dois roadmaps (Fraunces pros títulos, Public Sans pro corpo, IBM Plex Mono pros números) — o app real herda essa identidade, não começa do zero.

Tema claro/escuro — os tokens já cobrem os dois; o toggle na topbar grava a escolha no localStorage do navegador (preferência de tela, não dado da planilha).

Responsivo — mobile-first de verdade: layouts em grid/flex que colapsam pra 1 coluna abaixo de ~600px, tabelas longas (Histórico, Transações) viram cards empilhados no celular em vez de scroll horizontal forçado.

Estados de carregamento — esqueletos (blocos cinza do tamanho do conteúdo real) enquanto o Apps Script responde, nunca uma tela em branco; um indicador discreto "atualizado há Xmin" + botão de atualizar manual na topbar (já desenhado nos mockups).

Gráficos (Chart.js) — uma única fábrica de configuração em charts.js por tipo (linha, donut, barra, área), que lê as cores certas dos tokens do tema atual — garante que todo gráfico do app já nasce consistente e correto nos dois temas, em vez de estilizar cada gráfico na mão. Carregado com uma versão exata fixada no <script> do cdnjs (ex. 4.4.x) — nunca "latest", pra uma atualização da biblioteca não quebrar o app sem avisar.

Calendário de Proventos — não é gráfico: é um componente HTML/CSS próprio (grade de selos por mês + tabela de lançamentos), construído do zero seguindo os prints estilo Gorila. Vive em components.css como qualquer outro componente reutilizável.

Acessibilidade — contraste conferido nos tokens (já validamos a paleta), foco de teclado visível em todo controle interativo, aria-label em botões só-ícone, respeita prefers-reduced-motion.

Progressive Web App (instalável)

Decisão desta revisão: o site também fica instalável — ícone na tela inicial do celular, abre em tela cheia sem barra de navegador, e carrega o esqueleto instantaneamente mesmo com internet ruim. Não muda nada da arquitetura: continua HTML/CSS/JS estático, sem framework, sem build.

Manifest (manifest.json) — descreve o app pro sistema operacional: nome, ícones, cor de tema, e "display": "standalone" (é essa linha que tira a barra de endereço quando aberto pelo ícone). Um arquivo só, na raiz, referenciado por todas as páginas.

Ícones — jogo gerado a partir da mesma identidade visual dos mockups (192px, 512px, versão "maskable" pro Android recortar em círculo/quadrado, e um apple-touch-icon 180px pro iOS). Vivem em assets/icons/.

Service worker (sw.js) — guarda em cache só o esqueleto do app: HTML das páginas, CSS, JS, ícones. Nunca cacheia uma resposta do Apps Script, GOOGLEFINANCE ou BCB — dado financeiro sempre vem fresco da rede; esse cache é só pra abrir rápido, não pra mostrar número velho. Estratégia: cache-first pros arquivos estáticos (JS/CSS/ícones raramente mudam), network-first pro HTML de cada página (uma atualização de código chega rápido, mas o app ainda abre se a rede cair no meio do carregamento).

No iPhone — a Safari não mostra banner de instalação sozinha: você abre o site, toca em Compartilhar → "Adicionar à Tela de Início". A partir daí abre em tela cheia, como um app normal. A Safari também pode limpar o cache do service worker depois de ~7 dias sem uso — inofensivo aqui, porque o login já expira em ~1h e "ter que logar de novo depois de um tempo parado" já era o comportamento esperado, com ou sem PWA.

Toda página HTML ganha um blocinho fixo no <head> (link pro manifest, theme-color, apple-touch-icon, apple-mobile-web-app-capable) — repetitivo, mas são 5-6 linhas idênticas coladas em cada arquivo, sem lógica nenhuma envolvida.

Cache e atualização de dados

Cada resposta de leitura do Apps Script fica em cache no sessionStorage por alguns minutos (a cotação em si já atualiza devagar via GOOGLEFINANCE, então não faz sentido bater no Apps Script a cada clique de navegação entre páginas). O botão de atualizar da topbar força ignorar o cache e buscar de novo. Depois de qualquer escrita bem-sucedida (nova transação, meta salva), o cache daquela leitura específica é limpo na hora — você vê o resultado imediatamente, sem esperar o tempo normal de cache expirar.

Riscos técnicos e como mitigar

⚠Apps Script demora pra responder (1-3s por chamada, às vezes mais no primeiro acesso do dia) — e agora com 2 idas à rede por chamada (verificar token + ler/escrever), esse tempo tende a dobrar. Mitigado com esqueleto de carregamento, cache local, o indicador "atualizado há Xmin" em vez de recarregar toda hora, e — se precisar mais adiante — cachear a verificação do token por alguns minutos dentro do próprio Apps Script.
⚠GOOGLEFINANCE às vezes devolve erro temporário (#N/A) — os handlers do Apps Script tratam isso e devolvem "indisponível" em vez de quebrar a resposta inteira.
⚠Token de login expira (~1h) — api.js tenta renovar sozinho antes de te jogar de volta pra tela de login.
⚠Cota do Apps Script (execuções/dia, 6min por execução) — folgada demais pra uso de uma pessoa só; citada aqui só pra registro, não é uma preocupação real.
⚠Convenção de código — fórmulas escritas via Apps Script: a planilha está em locale pt-BR, então qualquer setFormula() precisa usar ; como separador de argumento (não vírgula) — mas os nomes de função continuam em inglês (DATE, TODAY, SUM...), nunca a versão em português (DATA, HOJE, SOMA). Confirmado via testarHistoricoGoogleFinance na Fase 0 — inglês+vírgula deu #ERROR!, português+; deu #NAME?, só inglês+; funcionou. Quando a fórmula é colada à mão direto na planilha (não via API), vale o oposto: nome da função em português.

Fora de escopo (de propósito)

Sem framework (React etc.), sem build tool, sem banco de dados adicional, sem servidor próprio pra manter — as duas únicas peças de infraestrutura são GitHub Pages e Apps Script, e as duas são gratuitas e gerenciadas pelo Google/GitHub. Isso mantém o projeto sustentável pra manter sozinho.

Passo 1 — Repositório GitHub e GitHub Pages

Fazemos isso primeiro porque o passo 2 (Google Cloud) precisa da URL final do site.

  • Se ainda não existe: crie um repositório novo em github.com/new (pode ser privado ou público — GitHub Pages funciona nos dois em conta pessoal).
  • Depois de ter pelo menos um arquivo index.html no repositório, vá em Settings → Pages, e em "Source" escolha a branch main, pasta / (root).
  • O GitHub mostra a URL final, algo como https://seu-usuario.github.io/nome-do-repo/. Guarde essa URL — é ela que vai no passo 2.

Me diga: se você já tem um repositório criado pro projeto (e qual o nome), ou se começamos um do zero.

Passo 2 — Client ID OAuth no Google Cloud Console

É o que permite o botão "Entrar com Google" existir no seu site. Não tem custo — é uma configuração, não um produto pago.

  • Acesse console.cloud.google.com logado com a mesma conta Google dona da planilha.
  • No topo, clique em "Selecionar um projeto" → "Novo Projeto". Dê um nome (ex. "App Investimentos") e crie.
  • Com o projeto selecionado, vá no menu (☰) → APIs e serviços → Tela de permissão OAuth.
    • Tipo de usuário: Externo (é a única opção disponível pra conta Gmail pessoal, e funciona normalmente).
    • Preencha nome do app, seu e-mail em "e-mail de suporte" e em "informações de contato do desenvolvedor". Salve e continue pelas telas seguintes sem mudar nada (escopos: nenhum adicional necessário).
    • Na tela "Usuários de teste", adicione o seu próprio e-mail Google. Isso mantém o app em modo "Teste" pra sempre — o que é exatamente o que queremos (só você consegue logar), sem precisar passar pelo processo de verificação do Google.
  • Vá em APIs e serviços → Credenciais → + Criar credenciais → ID do cliente OAuth.
    • Tipo de aplicativo: Aplicativo da Web.
    • Nome: qualquer um (ex. "App Investimentos - Web").
    • Em "Origens JavaScript autorizadas", adicione a URL do GitHub Pages do Passo 1 (só o domínio, sem caminho — ex. https://seu-usuario.github.io) e também http://localhost:8000 (ou a porta que formos usar no servidor local de desenvolvimento).
    • Não precisa preencher "URIs de redirecionamento" — o fluxo que vamos usar (botão de login) não usa redirecionamento.
    • Clique em Criar. A tela mostra um Client ID (termina em .apps.googleusercontent.com) — esse valor não é secreto, ele é feito pra ficar dentro do código do front-end. Guarde-o.

Passo 3 — Publicar o Apps Script como Web App

  • Abra a planilha → menu Extensões → Apps Script. Se já existir um projeto vinculado, use esse; senão, isso já cria um novo, vinculado à planilha (o que queremos — assim SpreadsheetApp.getActiveSpreadsheet() já sabe qual planilha usar, sem precisar do ID dela em lugar nenhum).
  • Quando o código de leitura/escrita estiver pronto (Fase 0), clique em Implantar → Nova implantação.
  • Tipo: Aplicativo da Web. Executar como: Eu. Quem tem acesso: Qualquer pessoa (a checagem de verdade é o e-mail dentro do código, como já explicado acima).
  • Na primeira implantação, o Google pede sua autorização pro script acessar a própria planilha — é normal, aceite.
  • Copie a URL que aparece (termina em /exec) — essa é a URL base que vai em api.js.
  • Em atualizações futuras do código: use Gerenciar implantações → editar (ícone de lápis) → Nova versão, nunca crie uma implantação nova do zero — assim a URL nunca muda.

Me diga: se a planilha já tem um projeto Apps Script vinculado a ela, ou se vamos criar um novo na Fase 0.
